# Aurora NixOS

NixOS modules and pinned Aurora hardware packages for Apple Silicon. The [native Aurora installer](https://github.com/aurora-silicon/aurora-installer) offers KDE Plasma, GNOME and minimal profiles.

The flake pins nixpkgs and the maintained [nixos-apple-silicon](https://github.com/nix-community/nixos-apple-silicon) module, then overlays Aurora's kernel, Mesa, Aura, U-Boot, audio profiles and services. `sources.json` records the same hardware source revisions used by the Fedora and ALARM ports. NixOS's declarative configuration, generations and rollback remain intact.

```sh
nix flake check --no-build
nix build .#checks.aarch64-linux.profiles
nix build .#aura .#uboot .#kernel .#mesa
```

`nixosConfigurations.aurora-kde`, `.aurora-gnome` and `.aurora-minimal` share the hardware module and kernel pin. Firmware is read from the target Mac's EFI partition at boot rather than embedded in a redistributable Nix store closure. No account password or device calibration is included in this repository.

Development status: KDE, GNOME and minimal development installer payloads and a signed binary cache are published. The refreshed kernel, AVD firmware and UPower changes are being qualified separately. Physical installation, encrypted first boot and device update/reboot validation remain pending. CI builds on native AArch64 and records output closures. Source evaluation and published artifacts do not establish hardware qualification.

First boot: KDE and GNOME images boot to a Plymouth splash (`spinner` theme, started in the systemd initrd, where it also asks for the disk password at every later start). On KDE, `aurora-firstboot` asks for the new disk password on that splash, replaces the temporary LUKS key and starts SDDM, which keeps the splash until its greeter appears, as GDM does; Plasma Setup then creates the owner account in `wheel`. nixpkgs packages Plasma Setup without a NixOS module, so `modules/plasma-setup.nix` declares its service, setup user, tmpfiles, polkit rules, KAuth helper and SDDM autologin rule, and `overlay.nix` patches its completion flag (`/etc/plasma-setup-done`) and the helper's `useradd` search for NixOS. On GNOME the same disk step runs on the splash, and GDM then starts GNOME Initial Setup's new-user mode, which creates the owner as an administrator (`wheel`). nixpkgs' GDM never starts that mode, so `modules/gnome-initial-setup.nix` runs a GDM built to find the setup session in the system profile (`aurora-gdm`), clears NixOS's "already run" marker before the display manager starts while no account exists, adds the `gnome-initial-setup` user GDM runs the session as, and declares the setup in `/etc/aurora/desktop-account-setup`; `overlay.nix` restores the account and password pages that nixpkgs' vendor file skips. Minimal images have no splash and keep the text wizard, which creates the account and protects the disk with one password. `aurora.firstboot=text` on the kernel command line selects the text wizard on a desktop that has no owner yet. Accounts created at first boot are imperative (`users.mutableUsers`), so rebuilds keep them.

The owner's first password sign-in at the greeter also becomes the disk password (aurora-firstboot 0.1.11 and later). NixOS generates `/etc/pam.d`, so `modules/firstboot.nix` declares those PAM hooks while `aurora.firstboot.passwordHooks` is true (the default). Once the password unlocks the disk, the hooks do nothing, and the rekey adds `aurora.firstboot.passwordHooks = false;` to the factory `/etc/nixos/owner.nix`, so the next rebuild removes them from PAM and later rebuilds never declare them again; a hand-edited `owner.nix` is left alone and the journal names the line to add. The disk password is typed in the initrd with `console.keyMap`. The module derives it from `services.xserver.xkb` with `mkDefault`, so the initrd prompt and the greeter type the same characters unless `console.keyMap` or `console.useXkbConfig` is set explicitly, and it declares the layout in `/etc/aurora/keyboard` for the rekey's comparison. See aurora-platform's README for where the temporary disk key lives until then.

Image basics: `scripts/build-image` runs `scripts/check-basics.py` on the installed root, reading the system closure through its store links. The build fails unless the image has a generated UTF-8 default locale (`i18n.defaultLocale` in the `LOCALE_ARCHIVE` the system uses), its desktop's terminal (Console or Konsole) with a launcher, GNOME's backgrounds or Plasma's wallpapers, NetworkManager enabled with the desktop's network settings, logind's lid-close suspend left in place, and a GRUB that finds /boot by filesystem UUID on the startup disk with hinted lookups only.

Remote login: every image includes the OpenSSH server, but it is off. No unit starts `sshd` or generates host keys at boot, and the firewall keeps port 22 closed. `sudo systemctl start sshd` starts it without a rebuild (host keys are made on first start); remote clients also need `sudo nixos-firewall-tool open tcp 22`, which lasts until the firewall reloads, or `services.openssh.openFirewall = true;`. `aurora.openssh.startAtBoot = true;` starts the server at every boot.

A future installed configuration imports `nixosModules.default` alongside the pinned Apple Silicon module, uses `overlays.default`, and supplies the target machine's disk and account configuration. The checked image module describes the native installer's ESP + boot + root layout; it is not a configuration to apply to an unrelated existing machine.


Native builds pass for Aura, U-Boot, the shared 7.3.0 kernel, Mesa, speakerguardd, Bankstown, Neo network configuration and aurora-bless. The kernel uses LLVM 22.1.8: an identical-input relink isolated invalid DWARF section references in lld 21, while lld 22 preserves them and passes BTF generation. Mesa uses Clang at normal release optimization, retaining all tests and the two-stage compiler-tool build; its driver closure excludes LLVM and SPIRV-Tools. These are build results, not device qualification.

`modules/platform.nix` wires the J700 guardian through its sense-PCM udev rule, retains feedback protection on other Macs, and enables Bluetooth userspace and the wireless regulatory database. The firmware helper checks this Mac's calibration/radio inputs before admission and defers Bluetooth until the runtime service before BlueZ.

`modules/camera-denoise.nix` runs aurora-camera-denoise, a PipeWire filter that denoises the built-in camera in low light, as a user service started with PipeWire. It only filters on boards listed in its board data. `aurora.cameraDenoise.enable = false;` turns it off, and `aurora.cameraDenoise.settings` writes `/etc/aurora-camera-denoise/denoise.conf`.

The cache tools are `scripts/export-cache` (an unsigned export of a build's closure), `scripts/sign-cache-metadata.py` (signs narinfo metadata in the publisher's protected job) and `scripts/prepare-cache-publication.py`. No build job holds the signing key. Cache clients verify signed NAR identities independently of their transport URLs. The public key is `keys/cache.pub`; publication and image qualification remain separate operations.

For an incremental snapshot, supply the last deployed cache directory with `--previous-metadata`. The preparer retains older entries and reuses their immutable Aurora release URLs only when the signed store identity and compressed transport identity match exactly. The current export's signatures are retained. Only new NAR files appear in the output `assets` directory; manifest rows with `reused_from` identify retained transport assets. Upload the actual files in `assets`, including the merged metadata archive, to the new release. The deployment workflow verifies every signed entry and its full NAR over HTTP, including reused assets, before replacing the public cache. Keep older releases available.

`publish-cache.yml` automates that preparation on native AArch64. It finds the newest cache release and the eligible native builds itself (explicit build IDs, base and tag remain optional inputs). The collector evaluates the committed Git flake, accepts only matching derivations and complete output sets from main-branch builds or manual builds whose commits have since been merged, verifies CI artifact digests and Nix signatures, and requires coverage of every current hardware output. It imports one bounded artifact at a time and retires extracted duplicates after verified merging. Run `deploy-cache.yml` for the resulting tag to verify the immutable HTTP assets before activating the cache; then build the desktop images.

The hardware stack includes the pinned Aurora AVD firmware and UPower forks. All decoder variants are built with their linked symbols in a separate `debug` output. UPower retains the upstream NixOS service and client contracts and runs the fork's macsmc regression tests. The shared 7.3.0 kernel also carries the accepted M4+ wait-state fix.

Source tracking, automatic publication, the `channel-testing` and `channel-stable` refs and the signing environments are described in [docs/updates.md](docs/updates.md).

Installed systems follow `channel-testing` (their `flake.lock` pins the installed commit). `sudo aurora-update` takes the newest signed update; every rebuild refreshes the ESP Stage 2 the way `update-m1n1` does on ALARM and Fedora, keeping `m1n1/boot.bin.old`, and never writes Stage 1. Nothing updates unattended. Installs from images before Alpha 10 need a one-time `flake.nix` edit, described in [docs/updates.md](docs/updates.md#moving-an-existing-install-to-the-channel-one-time).

Aurora defaults and the October 2026 Fedora changes are mapped in [the parity table](docs/fedora-parity-20261029.md). The shared module includes the locked-control ALSA restore fix, early sequencer, malcontent signal overrides, host and FEX guest Mesa, and Aurora's Flatpak GL extension for 25.08 and 26.08. Image assembly checks their actual payloads and initrd. The parity table records software verification; physical qualification remains separate.
